# 压测报告：虚拟线程 vs 平台线程

> 数据采集：2026-08-31，本机 12 核 / Windows 11 / JDK 21.0.11，零外部中间件。
> 报告由 `BenchMarkTest` 一键跑出并自动渲染（明细见 `target/bench-results.md`），本文在其基础上补结论与洞察。
> 同一天连跑多次：纯内存模拟场景（A~D）吞吐差异 <3%，可复现；HTTP 场景（E）抖动 ±10~20%，已改为 5 轮取中位数、并按区间表述。

## 一、测试环境

| 项 | 值 |
|---|---|
| 平台 / JDK | Windows 11 / JDK 21.0.11（12 核；虚拟线程调度器并行度默认 = 核数） |
| 依赖 | 仅 `spring-boot-starter`（空壳，不用 Web）+ JDK 并发 API，**零外部中间件** |
| 负载模型 | 闭环负载：`concurrency` 控制在途任务数，提交前取许可、完成后归还 |
| 被测实现 | `PLATFORM`（固定线程池 + 有界队列 + AbortPolicy） vs `VIRTUAL`（`newVirtualThreadPerTaskExecutor`） |
| HTTP 场景 | JDK 内置 `HttpServer` + `HttpClient`，唯一变量是 `setExecutor()` 传入的执行器 |

## 二、压测方式：一条命令跑完

场景矩阵定义在 `src/main/java/lan/chaos/virtualthread/bench/scenario/` 下五个场景类，由 `BenchRunner` 汇总：

```bash
cd chaos-java/jdk21-platform/jdk21-tech/jdk21-virtualthread-demo

mvn test -Dbench=true                      # 跑机制断言 + 压测矩阵（约 15s）
mvn test                                   # 只跑机制断言 + 引擎冒烟（秒级，压测默认跳过）
mvn spring-boot:run -Dspring-boot.run.arguments=--bench   # 以应用方式跑压测
```

- 压测核心抽为可复用引擎 `bench/BenchEngine.java`，测试与命令行共用同一条路径，数字口径一致。
- 压测默认不跑（`@EnabledIfSystemProperty(named = "bench", matches = "true")`）：矩阵是分钟级，且数据受机器负载影响，不适合做 CI 硬门禁。
- 断言只卡**方向性结论**（虚拟线程明显更快、pinning 明显更慢），不卡绝对值。

指标定义：`吞吐(任务/s)` = 成功数 / 墙钟耗时；`p50/p99` = **端到端**延迟（提交 → 完成，含排队）；`拒绝` = 被饱和策略拒掉的任务数；`峰值并发` = 真正同时执行的任务数峰值。

## 三、实测数据

### A. IO 密集吞吐（任务 4000，平台池固定 200 线程）

| 用例 | 模式 | 吞吐(任务/s) | p50(ms) | p99(ms) | 提升 |
|---|---|---|---|---|---|
| 并发 1000 / IO 20ms | 平台线程池(200) | 6,547 | 153.6 | 154.8 | — |
| | 虚拟线程 | 32,787 | 29.5 | 31.4 | **5.0 倍** |
| 并发 2000 / IO 20ms | 平台线程池(200) | 6,504 | 304.0 | 308.6 | — |
| | 虚拟线程 | 62,500 | 30.4 | 36.9 | **9.6 倍** |
| 并发 2000 / IO 100ms | 平台线程池(200) | 1,855 | 1075.7 | 1079.5 | — |
| | 虚拟线程 | 18,433 | 107.2 | 109.7 | **9.9 倍** |

几个表里看不出的点：

- **并发从 1000 涨到 2000，平台池吞吐纹丝不动（6,547 → 6,504）**，虚拟线程接近翻倍（32,787 → 62,500）。平台池的吞吐被 `线程数 / 单任务耗时` 锁死，多加的并发只变成队列长度，不变成吞吐——这是最硬的一条证据。
- **先崩的是尾延迟**：并发 2000 时平台池 p99 = 308ms，而单任务本身只阻塞 20ms，15 倍差距全来自排队。监控只看平均延迟会漏掉这段。
- 虚拟线程 p99 (31.4ms) 略高于单任务耗时 (20ms)，多出来的是调度与提交开销，属于正常水位。

### B. 饱和 → 排队 → 拒绝（任务 10000，在途 2000，池 100 + 队列 500）

| 模式 | 吞吐(任务/s) | 平均延迟(ms) | p50(ms) | 成功 | 拒绝 |
|---|---|---|---|---|---|
| 平台线程池(100,队列500) | 1,626 | 213.6 | 183.1 | 600 | **9,400** |
| 虚拟线程(无队列上限) | 32,573 | 61.2 | 61.4 | 10,000 | 0 |

- **别被平均延迟骗了**：平台池 avg 213ms 看着不致命，但 94% 的请求根本没被执行，是「快速失败」返回——拒绝的请求延迟接近 0，把平均值拉下来了。读这一组必须把「成功/拒绝」和吞吐放在一起看。
- 成功数 600 = 100 线程 + 500 队列，与承载上限精确吻合，说明引擎计数是准的（成功 600 + 拒绝 9,400 = 总投递 10,000，核算闭合）。
- 若换成**无界队列**，这里不会拒绝，但 p99 会一路飙升——本质是把压力转成延迟，不是消除压力。

### C. synchronized pinning 的代价（两组都用虚拟线程，任务 800，锁内阻塞 20ms）

| 模式 | 吞吐(任务/s) | p50(ms) | p99(ms) |
|---|---|---|---|
| 虚拟线程 + synchronized(阻塞) | 385 | 1,048.0 | 2,047.9 |
| 虚拟线程 + ReentrantLock(阻塞) | 25,806 | 30.8 | 31.2 |

- **换虚拟线程但不换锁 = 白换**：64 倍差距。pinned 版吞吐 385/s ≈ 12 核 / 20ms，退化到「载体线程数」的并发能力，与同规格平台线程池无异。
- 每个任务持有**自己的**锁（无锁竞争），差距纯粹来自 pinning 本身。
- 这是生产上最容易踩的坑：线程池换成了虚拟线程，但路径上还挂着 `synchronized` 的同步工具类或三方库，收益直接归零。JDK 24 的 JEP 491 才修复此问题。**注意**：pinning 的另一大来源是连接池/驱动等三方库内部的 `synchronized`。

### D. CPU 密集适用边界（纯计算 2ms × 3000，平台池线程数 = 核数）

| 模式 | 吞吐(任务/s) | p99(ms) |
|---|---|---|
| 平台线程池(12=核数) | 5,837 | 508.2 |
| 虚拟线程 | 5,871 | 504.0 |

- **1.01 倍 = 噪声**。平台池已按核数配到最优，虚拟线程再怎么调度也突破不了核数上限。
- 结论是**不要换**，而不是「换得更差」：CPU 密集任务换虚拟线程没有收益，还得额外付调度与栈内存开销。

### E. HTTP 服务：平台线程 vs 虚拟线程（请求 3000，单请求内阻塞 20ms）

| 服务端配置 | 模式 | 吞吐(请求/s) | p50(ms) | p99(ms) | 提升 |
|---|---|---|---|---|---|
| 池 50 线程 / 并发 300 | 平台线程池 | 1,894 | 153.7 | 172.9 | — |
| | 虚拟线程 | 7,246 | 42.2 | 59.3 | **3.8 倍** |
| 池 200 线程 / 并发 300 | 平台线程池 | 7,916 | 33.8 | 60.6 | — |
| | 虚拟线程 | 8,333 | 31.7 | 51.3 | **1.05 倍** |

> **本场景抖动明显，倍数要看区间。** 同一配置连跑 6 次：平台侧 6.1k~7.9k、虚拟侧 7.6k~11.0k（±10~20%）。因此本场景跑 **5 轮取中位数**，其余场景波动 <3%，不需要这么做。多次观测的提升区间：**池 50 → 3.8~5.4 倍，池 200 → 1.05~1.7 倍**。方向稳定，单点数字不可复现。

- **池越大差距越小**（多次观测一致）：50 线程时 3.8~5.4 倍，加到 200 线程只剩 1.05~1.7 倍。这说明「把线程池调大」确实能追一部分，代价是 200 个 OS 线程常驻（内存 + 上下文切换）。虚拟线程是用极少的载体线程拿到同等甚至更好的吞吐。
- **真实链路的提升倍数会被协议栈稀释**：同样 20ms 阻塞，纯内存模拟（场景 A）能差 5～10 倍，套上 HTTP 栈后只剩 1～5 倍。评估收益时要看「等待时间占整条链路的比例」——等待占比越高，虚拟线程收益越大。
- **抖动本身也是一条结论**：虚拟线程侧波动（7.6k~11.0k）明显大于平台侧，因为它不再被线程数限流、直接吃满 CPU 与网络栈，受机器负载影响更明显——说明瓶颈已经从「线程数」转移到了 CPU / 协议栈。

## 四、结论

| 场景 | 结论 | 量化 |
|---|---|---|
| IO 密集 | 虚拟线程吞吐随并发线性上涨，平台池被线程数锁死 | 5.0～9.9 倍 |
| 饱和 | 平台池拒绝请求，虚拟线程零拒绝 | 9,400 → 0 |
| pinning | `synchronized` 临界区内阻塞让虚拟线程退化 | 吞吐差 67 倍 |
| CPU 密集 | 无收益，瓶颈在核数不在线程模型 | 1.01 倍（噪声） |
| HTTP 服务 | 只换 executor 即可受益，池越小收益越大（抖动 ±10~20%，看区间） | 1.05～5.4 倍 |

一句话：**虚拟线程买的是「等待」的时间，不是「算力」**。IO 等待占比越高、并发越大，收益越大；CPU 密集任务别换；换的同时必须排查 `synchronized` 临界区内的阻塞调用。

## 五、过程中修复的问题（供回查）

1. **拒绝数被算成两倍**：`ExecutorFactory` 的 `RejectedExecutionHandler` 里 `rejected.incrementAndGet()` 后又抛异常，`BenchEngine` 捕获时再 +1 → 场景 B 出现「成功 600 + 拒绝 18,800 = 19,400 > 任务数 10,000」。改为工厂只抛异常、由引擎统一计数，修复后核算闭合（600 + 9,400 = 10,000）。
2. **HTTP 场景偶发 17 例建连失败**：`HttpServer.create(addr, 0)` 的 backlog 用系统默认值，并发建连阶段偶发连接被拒，被记成业务失败。改为显式 backlog = 1024，失败归零。
3. **压测拖慢日常测试**：完整矩阵 13s+ 且数据受机器负载影响。用 `@EnabledIfSystemProperty` + surefire `systemPropertyVariables` 隔离，默认跳过，另拆 `BenchSanityTest` 用极小参数守住「引擎算得对」这条底线。
4. **`HttpClient` 的 executor 泄漏**：`.executor(Executors.newVirtualThreadPerTaskExecutor())` 把执行器直接 new 进 builder、不留引用，之后再也没法关闭，连跑多轮会不断累积。改为持有引用并在 `finally` 关闭（客户端的回调执行器与压测并发载体分开建，避免职责混用）。
5. **`abortOnReject` 是死配置**：`BenchOptions` 定义了这个字段但 `ExecutorFactory` 从不读取，饱和策略永远是 AbortPolicy，读代码的人会以为能切换。直接删掉字段——用注释说明「为何不用 CallerRunsPolicy」，比留一个不生效的开关诚实。
6. **延迟分位重复排序**：`LatencyRecorder` 的 p50/p99/avg/max 各自复制并排序整个数组，一份结果排了 4 次。改为 `stats()` 一次排序返回全部统计量。
7. **HTTP 场景单次采样不可信**：连跑 6 次，虚拟线程侧吞吐 7.6k~11.0k（±10~20%），单次数字写出来第二天就复现不了。改为 5 轮取中位数，并在报告中标注观测区间。
8. **pinning 场景参数误导**：报告里照抄 `options.describe()` 会显示「平台池线程=200」，但该场景两组都是虚拟线程、根本不涉及平台池。改为自定义参数描述。

## 六、复现与扩展

- 改载体线程数观察联动：`-Djdk.virtualThreadScheduler.parallelism=8`（场景 C 的 pinned 吞吐会随它线性变化）。
- 定位生产 pinning：`jcmd <pid> Thread.dump`、`-Djdk.tracePinnedThreads=full`。
- 场景参数集中在各 `BenchXxx` 类的常量与 `BenchOptions`，改参数即可跑自己的档位；结果自动落到 `target/bench-results.md`。
